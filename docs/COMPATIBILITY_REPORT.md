## 🔴 Critical finding #1 — Two separate, non-communicating databases

This is the most important issue in the project right now and should be
the team's top priority before anything else.

**What's happening:**

- `backend/` (built by the DB/MCP teammate) has its own PostgreSQL database,
  its own `User` / `Branch` / `Stock` SQLAlchemy models, its own JWT auth,
  and exposes a full REST API (`/auth`, `/users`, `/branches`, `/stocks`,
  `/internal/...`). This looks like it was built to be **the** shared
  database for the whole project (Task 1).
- `backoffice/` (built by Collins) has **its own separate SQLite database**
  (`backoffice.db`), its **own** `User` / `Branch` / `Stock` models (similar
  shape, but a distinct schema), its own password hashing, its own JWT
  logic — and never calls the `backend` service at all. It seeds its own
  admin account (`admin` / `admin123`) and its own branches ("Downtown
  Branch", "Uptown Branch"), completely independent from `backend`'s seed
  data (`admin` / `Admin123!`, different branch names).

**Why this is a problem:** the project only makes sense with **one** source
of truth for users, branches, and stock. Right now:
- A user created via the Backoffice's admin page only exists in
  `backoffice.db` — the `backend` (and therefore the MCP server and the AI
  agent) has no idea it exists.
- Stock changes made in the Backoffice UI never reach the database the AI
  Query Service reads from (via the MCP server → `backend`'s `/internal`
  routes). **The chatbot and the Backoffice are currently looking at two
  different worlds.**
- Running both together (see `docker-compose.yml`) also caused a **port
  collision** — both wanted `:8000`. I changed the Backoffice's exposed
  port to `:8003` in the combined `docker-compose.yml` just so both can
  run at the same time without crashing, but that's a workaround, not a fix.

**What the team needs to decide (this is a team conversation, not
something I resolved unilaterally, since it means real code changes to
Collins's part):**

- **Option A (recommended):** Rework `backoffice/` to call `backend`'s API
  instead of querying its own local database. Concretely: replace direct
  `db.query(User)...` / `db.query(Stock)...` calls in
  `backoffice/app/routers/*.py` with HTTP calls to `backend`'s `/auth`,
  `/users`, `/stocks` endpoints (which already exist and already do
  password hashing, soft-delete, quantity validation, etc.). This keeps a
  single source of truth and matches the project's stated architecture
  (one relational database, shared by the Backoffice).
- **Option B:** Point `backoffice/app/database.py`'s `DATABASE_URL` at the
  same PostgreSQL database `backend` uses, and align the two `models.py`
  files so they describe the exact same tables (same column names, same
  constraints). Faster than Option A, but now two independent codebases
  both talk directly to the same tables, which risks subtle bugs if they
  drift out of sync again.

Either way, someone needs to update `backoffice/`'s data layer — this
can't be resolved by just merging files.

## 🟡 Finding #2 — The AI agent bypasses the real MCP server

The project asks (Task 5.2) for the AI agent to connect **through the
Product MCP Server**. What's actually wired up right now:

- `product_mcp_server/mcp_server.py` is a real MCP server (using the
  official `mcp` Python SDK, `FastMCP`, stdio transport) — this is the
  "true" Task 4 deliverable, and it works as a standalone MCP server.
- However, `ai_service/agent.py` doesn't talk to it. It imports
  `mcp_client.py`, which is a **direct HTTP client** that duplicates the
  same logic (calls the Product API and `backend`'s `/internal` routes
  directly), bypassing the MCP protocol entirely.
- The MCP server's own README acknowledges this directly: *"Pendant le
  développement local, votre collègue peut importer directement le module
  client [...] En production ou conteneurisé via Docker, l'agent IA se
  connecte au serveur MCP via STDIO ou SSE."* — so this was a known,
  intentional dev shortcut, not an oversight, but it's still not the final
  intended architecture.

**Why it still works today:** `mcp_client.py`'s functions
(`get_product_details`, `check_stock`, `list_branch_inventory`,
`list_products`, `search_products`) were written with the **exact same
signatures** as the `mcp_client_mock.py` Tété was using, so it's a
drop-in replacement — that's why the swap in `agent.py`
(`import mcp_client_mock as tools` → `import mcp_client as tools`) worked
immediately with no other changes needed. Good compatibility work on the
teammate's part.

**What's left to close this gap** (optional, weigh against your
deadline): connect `agent.py` to `mcp_server.py` using a real MCP client
(the `mcp` Python SDK's `ClientSession`, spawning `mcp_server.py` as a
subprocess over stdio). This is real extra work, not a small tweak — if
time is short, documenting the current approach as a deliberate,
justified simplification in your README (citing the trade-off: faster to
build and debug locally vs. strictly following the MCP protocol) is a
defensible choice for a school project, as long as you can explain it
if asked.

## 🟡 Finding #3 — Real MCP server tool contract differs slightly from what `agent.py` expects

If the team does decide to wire up the real MCP server later, note these
mismatches between `product_mcp_server/mcp_server.py`'s tools and the
`TOOL_DEFINITIONS` in `agent.py`:

| Tool | `agent.py` expects | Real MCP server provides |
|---|---|---|
| `check_stock` | `product_id`, optional `branch_id` | only `product_id` (no branch filter — always returns all branches) |
| `list_branch_inventory` | param named `branch_id`, format like `BR-1` | param named `branch_identifier`, accepts a name (`"Paris"`), a raw id (`"1"`), or `BR-01`-style codes |
| `list_products` | optional `category` filter | no filter support |
| `search_products` | expected by `agent.py` | **not implemented** in the real MCP server at all |
| `list_branches` | not expected by `agent.py` | exists in the real MCP server, unused currently |

None of this breaks anything today, since `agent.py` currently talks to
`mcp_client.py` (which *does* match the expected contract) rather than to
`mcp_server.py` directly. This table only matters if/when the team
connects the agent to the real MCP server for real.

## 🟢 Finding #5 — Demo/seed data is inconsistent across services

- `backend/app/seed.py`: seeds `admin` / `Admin123!` and `employee` /
  `Employee123!` (per its README)
- `backoffice/main.py`: seeds `admin` / `admin123`, and branches "Downtown
  Branch" / "Uptown Branch"
- `ai_service/mcp_client_mock.py` (Tété's, no longer used once wired to
  the real client): `HB-LAP-1001`, `HB-KEY-2003`, branches `BR-1`/`BR-2`
- `docker-compose.yml`'s placeholder Product API: `HB-LAP-1001`,
  `HB-KEY-2003`, `HB-MON-3005`

This is a direct symptom of Finding #1 (two databases). Once the team
picks Option A or B above, this resolves itself — there will only be one
seed script to keep consistent.
